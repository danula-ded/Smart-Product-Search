# BPMN Search Flow

Простая BPMN-схема для защиты. Без лишней детализации, но с нашими модулями, точками принятия решений и тем, как это влияет на выдачу.

## Что рисовать

### Пулы и дорожки

- Пул `Заказчик`
  - Дорожка `Пользователь`
- Пул `Smart Product Search`
  - Дорожка `Web UI`
  - Дорожка `API`
  - Дорожка `Search Engine`
  - Дорожка `Profile Engine`
  - Дорожка `SQLite Storage`

## Сценарий 1. Подготовка данных и индекса

### Короткая BPMN-цепочка

1. Start Event: `Система готовится к работе`
2. Service Task `Загрузить встроенный датасет или принять дозагрузку`
3. Service Task `Провести schema detection и очистку строк`
4. Service Task `Импортировать СТЕ`
5. Service Task `Построить product_fts и lexicon`
6. Service Task `Импортировать контракты`
7. Service Task `Построить customer_profiles`
8. Service Task `Сформировать demo-профили`
9. End Event: `Индекс и профили готовы`

### Что подписать рядом

- Data Store: `products`
- Data Store: `contracts`
- Data Store: `product_fts`
- Data Store: `customer_profiles`
- Data Store: `lexicon`

### Что это дает

- `product_fts` влияет на быстрый поиск кандидатов
- `customer_profiles` влияет на персонализацию
- `lexicon` влияет на исправление опечаток

## Сценарий 2. Поиск и персонализация

### Основная BPMN-цепочка

1. Start Event: `Пользователь начинает поиск`
2. User Task `Ввести запрос и выбрать заказчика`
3. Service Task `Нормализовать запрос`
4. Exclusive Gateway `Есть раскладка / опечатка / синоним?`
5. Service Task `Скорректировать запрос и собрать searchTermsUsed`
6. Service Task `Извлечь кандидатов через SQLite FTS5`
7. Exclusive Gateway `Есть профиль заказчика?`
8. Service Task `Добавить history boosts`
9. Exclusive Gateway `Есть события текущей сессии?`
10. Service Task `Добавить session boosts / penalties`
11. Service Task `Собрать explanation и score breakdown`
12. User Task `Показать персонализированную выдачу`
13. End Event: `Пользователь видит результат`

### Что принимается на gateway и как влияет

#### Gateway `Есть раскладка / опечатка / синоним?`

- Да:
  - меняется `correctedQuery`
  - расширяется `searchTermsUsed`
  - увеличивается шанс найти релевантный товар
- Нет:
  - используется исходный нормализованный запрос

#### Gateway `Есть профиль заказчика?`

- Да:
  - добавляются `history_product`, `history_category`, `history_tokens`
  - выше поднимаются товары, похожие на прошлые закупки заказчика
- Нет:
  - остается только базовый lexical ranking

#### Gateway `Есть события текущей сессии?`

- Да:
  - добавляются `session_product` и `session_category`
  - выдача сразу меняется после действий пользователя
- Нет:
  - выдача строится без live-overlay

## Сценарий 3. Динамическое изменение выдачи

### BPMN-цепочка

1. Start Event: `Пользователь взаимодействует с результатом`
2. User Task `Открыть карточку / быстро вернуться / сохранить / отметить релевантным / отметить нерелевантным`
3. Service Task `Записать событие в events`
4. Service Task `Обновить session overlay`
5. User Task `Повторить похожий запрос`
6. Service Task `Пересчитать ранжирование с учетом новых сигналов`
7. User Task `Увидеть измененную выдачу`
8. End Event: `Динамическая персонализация подтверждена`

### Что подписать рядом

- Data Store: `events`
- Annotation: `Без полной переиндексации`
- Annotation: `Меняется только overlay ранжирования`

## Простой вид схемы для draw.io / Camunda

Если нужно нарисовать совсем быстро, перенеси в редактор вот такую структуру:

### Блок 1. Offline подготовка

`Start -> Импорт СТЕ -> Построение FTS -> Импорт контрактов -> Построение профилей -> End`

### Блок 2. Online поиск

`Start -> Ввод запроса -> Нормализация -> Gateway "Нужна коррекция?" -> FTS retrieval -> Gateway "Есть профиль?" -> Gateway "Есть session signals?" -> Explanation -> Показ выдачи -> End`

### Блок 3. Live-обратная связь

`Start -> Действие пользователя -> Запись события -> Обновление overlay -> Повторный поиск -> Измененная выдача -> End`

## Короткие подписи для элементов

Используй короткие названия, чтобы схема не выглядела перегруженной:

- `Нормализация запроса`
- `Исправление раскладки`
- `Опечатки и синонимы`
- `FTS5 retrieval`
- `История закупок`
- `Сигналы сессии`
- `Explanation`
- `Events`
- `Profiles`

## Что сказать по этой схеме на защите

- У нас есть offline-часть и online-часть.
- Offline-часть строит индекс товаров, словарь и профили заказчиков.
- Online-часть обрабатывает запрос, быстро ищет кандидатов и потом персонализирует их.
- После действий пользователя глобальный индекс не перестраивается, но меняется overlay ранжирования.
- За счет этого выдача меняется сразу, а не после долгой переиндексации.

## Самая простая версия BPMN в одну фразу

`Данные -> Индекс и профили -> Запрос -> Нормализация -> FTS5 -> Персонализация -> Explanation -> Действие пользователя -> Обновление сигналов -> Новый результат`
