# Requirements Audit

Дата проверки: 2026-04-04

## Executive Summary

Текущее решение соответствует основному ТЗ как рабочий demo-ready MVP:

- есть веб-интерфейс и backend без внешних API;
- поиск работает на полном датасете;
- персонализация строится по истории контрактов и live-событиям;
- опечатки, раскладка и синонимы учитываются в рантайме;
- выдача перестраивается после действий пользователя в той же сессии;
- есть экран метрик и подготовленная BPMN-документация.

Главные оставшиеся риски перед защитой:

- морфология реализована эвристически, а не через полноценный лемматизатор;
- полный импорт большого датасета занимает десятки минут и должен быть прогрет заранее;
- в тестах остались framework warnings от FastAPI/Pydantic alias schema generation, но они не ломают runtime.

## How AI Is Used

ИИ в текущем решении используется прагматично:

- основной поиск работает без LLM;
- весь обязательный hot path закрыт локальными правилами, словарями, SQLite FTS5 и rerank;
- локальная LLM может быть включена как optional parser для неоднозначных запросов;
- объяснение результатов строится детерминированно, а не генеративно.

Это соответствует хакатонному ограничению: без внешних API и без неоправданно тяжелой модели в каждом запросе.

## How Real-Time Preference Recalculation Works

Персонализация идет в два слоя:

1. Долгоживущий профиль:
   - строится из таблицы `contracts`;
   - сохраняет веса по категориям, СТЕ и токенам;
   - влияет на каждый запрос конкретного заказчика.

2. Live session overlay:
   - события `result_opened`, `result_saved`, `marked_relevant`, `marked_irrelevant`, `result_bounced` пишутся в `events`;
   - после записи события пересчитывать глобальный индекс не нужно;
   - следующий поиск учитывает product/category penalties and boosts из текущей сессии.

Именно поэтому выдача меняется сразу после действия пользователя.

## What Was Fixed During Final Audit

- убран deprecated startup/shutdown lifecycle и переведено на `lifespan`;
- добавлен persistent cache для `/metrics/summary`;
- исправлен UI-баг на вкладке `Данные`, из-за которого после рестарта не показывался последний import job;
- убраны дубли атрибутов в explanation и product payload на карточках выдачи;
- повторно подтверждено отсутствие дублей `product_fts` по одному `ste_id`.

## Remaining Gaps

1. Морфологический слой не полноценный.
   Сейчас это качественная нормализация, раскладка, typo correction, synonyms и FTS5. Для демо этого достаточно, но это не отдельный лемматизатор уровня full morphology engine.

2. Полный import тяжелый.
   На полном наборе его нужно запускать заранее, а не во время защиты.

3. Остались Pydantic/FastAPI schema warnings в тестах.
   Runtime они не ломают, но это незакрытый технический хвост.

4. BPMN пока не экспортирован в финальную визуальную диаграмму.
   Для защиты нужен png/svg/pdf поверх существующего markdown-черновика.

## Optimization Priorities

Самые полезные улучшения перед защитой или после нее:

1. Добавить легковесную морфологическую нормализацию для русского языка.
   Это даст лучший recall по словоформам.

2. Ускорить broad-query retrieval.
   Самые медленные запросы сейчас возникают там, где synonym expansion сильно раздувает FTS-term set.

3. Закэшировать lexicon в памяти процесса.
   Сейчас он берется из SQLite на каждом запросе, что можно сделать дешевле.

4. Ограничить и калибровать synonym expansion по классу токена.
   Это сократит шум и ускорит retrieval.

5. Довести визуальную BPMN и demo-script.
   Это даст прямой выигрыш на защите без риска сломать runtime.

## Bottom Line

Если оценивать по сути ТЗ, а не по косметике, система уже готова к демонстрации:

- работает на полном датасете;
- дает персонализированную выдачу;
- объясняет результат;
- показывает typo correction, keyboard layout correction и synonyms;
- динамически меняет выдачу после действий пользователя;
- имеет measurable quality lift и живой веб-интерфейс.

Главное, что осталось сделать перед выступлением:

- не пересобирать тяжелый импорт прямо на сцене;
- подготовить визуальную BPMN;
- прогреть один раз сервер и метрики;
- идти по заранее выбранным кейсам в UI.
